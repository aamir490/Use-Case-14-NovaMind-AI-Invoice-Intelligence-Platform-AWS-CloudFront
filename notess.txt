## 1. User Login and React Frontend Delivery

* Why this service is used: Amazon CloudFront acts as a global Content Delivery Network (CDN) to cache and serve static assets at low latency. Amazon S3 provides highly durable, cost-effective static website hosting for the React single-page application (SPA).
* What data moves: The browser requests the application; CloudFront delivers the compiled React + TypeScript + Vite + Tailwind bundle to the user’s machine.
* Process Type: Synchronous.

## 2. Cognito Authentication and JWT-Based Tenant Isolation

* Why this service is used: Amazon Cognito User Pool offloads identity management, sign-up, and sign-in operations securely without custom authentication backend code.
* How Cognito tenant isolation protects user data: When a user authenticates, Cognito issues a cryptographically signed JSON Web Token (JWT). The token contains a sub claim unique to that user, which maps directly to a tenant_id in the application logic. Every database row in DynamoDB is structured with a composite primary key starting with tenant_id. Every single Lambda function extracts this tenant_id from the decoded token context, ensuring a tenant can never read, modify, or delete another tenant's invoice data.
* What data moves: User credentials go to Cognito; JWT access/identity tokens return to the React SPA.
* Process Type: Synchronous.

## 3. API Gateway Request Flow and Pre-signed S3 Upload URL

* Why this service is used: Amazon API Gateway hosts the REST API endpoints, managing routing, CORS policies, and verifying JWT tokens natively via a built-in Cognito JWT Authorizer. Upload API Lambda executes the backend code to reserve database state and generate secure upload parameters.
* What data moves: The browser sends a POST /invoices/upload-url request with the JWT in the header. The Upload API Lambda logs a job entry (PENDING) in the Processing Jobs DynamoDB Table and contacts S3 to generate a time-limited (5-minute) pre-signed upload URL, which is returned to the browser.
* Process Type: Synchronous.

## 4. Direct Invoice Upload from Browser to S3

* Why this service is used: Pushing binary files (PDFs/Images) directly to Amazon S3 protects downstream API layers from payload constraints (API Gateway has a strict 10MB payload limit) and saves costly Lambda execution time that would otherwise be spent buffering file bytes in memory.
* What data moves: The browser performs an HTTP PUT request containing the raw invoice file (PDF, PNG, JPG, or TIFF) directly to the S3 Invoice Uploads Bucket using the pre-signed URL.
* Process Type: Synchronous from the browser's viewpoint, but it marks the boundary where the architecture shifts into an asynchronous background processing model.

## 5. S3 Event → SQS Queue → SQS Trigger Lambda

* Why these services are used: Amazon SQS acts as a durable message buffer to smooth out sudden transaction spikes. If a user uploads 10,000 invoices at once, SQS holds the events safely so downstream components aren't overwhelmed.
* How the architecture handles failed SQS messages using a Dead-Letter Queue (DLQ): If the SQS Trigger Lambda encounters an unexpected error and fails to process a message, the message returns to the queue. If it fails 3 consecutive times (the Max Receive Count parameter), SQS automatically reroutes it to the SQS Dead-Letter Queue (DLQ). This isolates corrupt files or unhandled edge cases without blocking the main traffic line and alerts engineers to investigate.
* What data moves: S3 sends an ObjectCreated event notification to SQS. The SQS Trigger Lambda consumes this payload containing the bucket name and file key.
* Process Type: Asynchronous.

## 6. Step Functions Express Orchestration

* Why this service is used: AWS Step Functions Express is optimized for high-volume, short-duration event-driven workflows.
* Why SQS and Step Functions are used instead of one large Lambda: A single monolithic Lambda function processing an invoice would suffer from high cost, structural fragility, and strict time limit risks. It would have to sit idle while waiting for external APIs like Textract and Bedrock to respond, paying for idle CPU time. By breaking the workload into Step Functions, each stage is its own isolated Lambda function. Step Functions handles state transitions, retries, conditional routing, and error flows natively, yielding lower costs and higher durability.
* What data moves: The execution input context (bucket name, file key, and metadata) is passed sequentially from stage to stage.
* Process Type: Asynchronous.

## 7. OCR Lambda Calling Amazon Textract AnalyzeExpense

* Why this service is used: Amazon Textract goes beyond basic optical character recognition; its AnalyzeExpense API natively understands document geometry, automatically identifying unstructured financial documents to extract tax fields, line items, totals, and vendor details out of the box.
* What data moves: The OCR Lambda tells Textract where the document resides in S3. Textract parses the document and returns highly structured OCR JSON data back to the Lambda function.
* Process Type: Asynchronous execution within the workflow step.

## 8. AI Analysis Lambda Calling Amazon Bedrock Nova Micro

* Why this service is used: Amazon Bedrock provides fully managed access to leading foundational models via a secure API. Amazon Nova Micro (us.amazon.nova-micro-v1:0) is chosen for this platform because it offers ultra-fast inference speeds and low transaction costs while executing complex structured JSON outputs perfectly.
* What happens when Amazon Bedrock fails or is throttled: The Step Functions pipeline is configured with explicit retry logic and fallbacks. If Bedrock hits a rate limit or service interruption, Step Functions catches the error code and backs off exponentially before retrying. As noted in the diagram, if the error persists, the AI failure is treated as non-fatal—the function fills the anomaly payload with an empty array, logs the issue, and allows the core processing pipeline to complete successfully rather than crashing the entire transaction.
* What data moves: The AI Analysis Lambda compiles a prompt containing the raw text, extracted OCR fields, and a strict JSON schema template. It sends this to Bedrock via InvokeModel, receiving back a clean JSON array detailing anomalies, a textual summary, and a confidence score.
* Process Type: Asynchronous pipeline step.

## 9. Risk Scoring Lambda Combining LLM Anomalies with Deterministic Rules

* Why these components are used: This function executes a Deterministic Python Rules Engine.
* Why Bedrock and deterministic rules are used together: LLMs excel at abstract pattern matching (e.g., detecting if an invoice description looks unusually vague or suspicious compared to typical patterns), but they can struggle with strict mathematical calculations and exact compliance verification. The architecture pairs them: Bedrock isolates structural anomalies, while the Python rules engine handles concrete logic checks (e.g., matching if Subtotal + Tax == Total, verifying if mandatory fields are missing, or cross-checking duplicates). This guarantees zero hallucinations for critical mathematical compliance.
* What data moves: It inputs the combined OCR structures and AI anomalies, processing them to produce a final calculated risk score from 0 to 100 alongside an explicit classification tier (LOW, MEDIUM, or HIGH).
* Process Type: Asynchronous pipeline step.

## 10. Store Results Lambda Writing Data to DynamoDB and Extracted Text to S3

* Why these services are used: Amazon DynamoDB serves as a high-speed NoSQL database capable of consistent single-digit millisecond read/write actions at any scale. A secondary S3 Processed Text Bucket stores raw text files cleanly, keeping database items light and optimizing query costs.
* What data moves: The Store Results Lambda writes the enriched metadata record (tenant details, extracted fields, risk rankings, and AI summaries) into the Invoices DynamoDB Table and marks the Processing Jobs Table as COMPLETED. Simultaneously, it writes a .txt file of the raw extracted data to the S3 Processed Text bucket and posts a lifecycle notification to EventBridge.
* Process Type: Asynchronous pipeline step.

## 11. EventBridge and SNS High-Risk Alerts

* Why these services are used: Amazon EventBridge serves as a serverless event bus that filters system-wide messages based on strict rules. Amazon SNS handles global publish/subscribe notification deliveries natively.
* What data moves: The pipeline emits an InvoiceProcessed event into EventBridge. EventBridge evaluates a custom json filter: risk_level = HIGH. If matched, it immediately triggers the attached Amazon SNS Topic, which fans out an urgent high-risk email notification to system administrators.
* Process Type: Asynchronous.

## 12. Frontend Polling the API and Showing Invoice Intelligence

* Why these services are used: Standard polling endpoints let frontends remain highly responsive and secure without maintaining open, resource-heavy WebSocket connections.
* What data moves: The browser periodically checks GET /invoices/{id}/status through API Gateway. When the status toggles to COMPLETED, the UI requests GET /invoices/{id}. The Invoices API Lambda reads the record from the database and returns the structured data, empowering the dashboard to render charts, detail views, risk ratings, and full anomaly analytics.
* Process Type: Synchronous.

## 🛡️ Security, Monitoring, and Deployment Infrastructure## 13. Security, Monitoring, and Operational Capabilities

* How this system scales without managing servers: Every single component used—CloudFront, S3, Cognito, API Gateway, Lambda, SQS, Step Functions, DynamoDB, Textract, Bedrock, and EventBridge—is inherently serverless. There are no virtual machines to patch, no operating systems to maintain, and no load balancers to configure. Scalability is handled automatically by AWS: Lambda scales horizontally by spinning up concurrent containers based on request rates, SQS adjusts dynamically to handle millions of queued items, and DynamoDB provisions on-demand read/write throughput instantly.
* AWS IAM Roles: Implements strict least-privilege security. Every Lambda function is bounded by an execution-specific IAM role, ensuring the Upload Lambda can only write to the upload bucket and jobs table, while the AI Analysis Lambda only has permissions to invoke Bedrock.
* Amazon CloudWatch & AWS X-Ray: CloudWatch collects operational performance metrics, application standard output logs, and handles infrastructure alarms. AWS X-Ray enables distributed tracing across the microservices, appending a trace ID to requests as they transition from API Gateway through Lambda, SQS, and Step Functions, making debugging latency bottlenecks straightforward.
* AWS CDK v2 Deployment: The entire system infrastructure is codified in clean TypeScript using the AWS Cloud Development Kit (CDK). This breaks the deployment architecture into clean, reusable stacks (Storage, Authentication, Processing, API, Frontend), ensuring repeatable deployments across different environments (Dev, Staging, Production).

## ❓ 5 Likely Interviewer Questions & Strong Answers## 1. Why did you use Step Functions Express instead of Step Functions Standard?
Answer: "Step Functions Express is explicitly designed for high-volume, short-duration event-driven processes lasting under five minutes. It offers much higher throughput capacities (over 100,000 executions per second) and significantly lower costs compared to Standard workflows, which are geared toward long-running human-in-the-loop steps. Since our invoice processing stages run sequentially in seconds, Express is the ideal, budget-conscious choice."
## 2. Why did you implement a backend polling mechanism instead of using WebSockets via API Gateway?
Answer: "While WebSockets provide real-time updates, they require the application client to maintain active stateful connections, which adds architectural complexity and cost to a serverless platform. Since invoice analysis typically completes within a few seconds, an optimized short-polling or exponential backoff polling mechanism over standard HTTPS routes provides a simpler, stateless execution profile that handles scale elegantly with minimal overhead."
## 3. If the Invoices Table scales to millions of rows, how do you prevent performance degradation on your GET /invoices list queries?
Answer: "We use DynamoDB's native partition key design to isolate data efficiently. The table uses tenant_id as the Partition Key (PK) and invoice_id as the Sort Key (SK). When a user pulls their invoice list, the Invoices API Lambda runs a fast, targeted Query command filtered by their specific tenant_id rather than performing a slow, expensive table Scan. This ensures lookup times remain consistently in the single-digit milliseconds, regardless of total table growth."
## 4. Why did you choose the Amazon Nova Micro model over a larger foundational model like Nova Pro or Claude Sonnet?
Answer: "Invoice anomaly detection requires precise textual processing, format validation, and structured output formatting rather than deep reasoning or creative writing capabilities. By designing an explicit JSON schema prompt and pairing it with Amazon Nova Micro, we get fast response times and low token costs while still capturing structural anomalies accurately. For mathematical checks, we use a deterministic Python engine, which lets us offload heavy computation away from the LLM entirely."
## 5. How does your architecture handle sudden API rate limits or throttling from Amazon Bedrock during high-traffic intervals?
Answer: "We handle this through two defensive layers: workflow-managed retries and structural decoupling. Step Functions natively handles Bedrock.ThrottlingException errors by executing automatic retries with exponential backoff. If the model fails repeatedly after these attempts, the failure is caught gracefully at the code level within the AI Analysis Lambda. The function populates the anomaly payload as empty and allows the pipeline to complete successfully, ensuring the invoice is processed and stored rather than failing the transaction."

Next, a specialized AI assistant reviews the text to spot anything unusual or suspicious, like vague descriptions or hidden fees.
