**Analysis date:** 26 September 2026  
**Method:** Read-only inspection of source code, infrastructure, configuration, workflows, tests, documentation, and relevant images.

**No files were created, modified, deleted, renamed, or moved. No packages were installed, deployments performed, or application requests sent to AWS.** The final Git status was clean.

Builds and tests were not executed. Test findings below come from source inspection, not a claimed successful test run. Historical screenshots and deployment transcripts support past activity; they do not establish current AWS availability.

## 1. Executive Summary

NovaMind AI is an **event-driven, serverless invoice analysis application** with a React frontend and Python AWS Lambda backend.

It addresses a practical problem: invoices arrive as images or PDFs, while reviewers need searchable fields, explanations of suspicious content, and a consistent way to prioritize review.

The implemented processing path is:

1. A user authenticates through Amazon Cognito.
2. The browser requests a temporary S3 upload URL.
3. The browser uploads the invoice directly to S3.
4. S3 sends an event to SQS.
5. A trigger Lambda starts a Step Functions Express workflow.
6. Textract extracts invoice fields and text.
7. Bedrock Nova Micro analyzes the extracted content.
8. Python rules combine deterministic checks with AI findings.
9. Results are stored in DynamoDB, with extracted text in S3.
10. The frontend reads status, invoice details, and aggregate analytics.

The repository contains substantial implementation: eight application Lambda functions, five CDK stacks, a frontend, unit tests, and GitHub Actions workflows.

**Maturity assessment:** a substantial prototype or demonstration application with production-oriented foundations. It is **not defensibly production-ready** from the inspected evidence.

The most important gaps are:

- Missing ownership verification on the processing-job status fallback.
- Browser query caches that are not separated or cleared by user.
- Duplicate processing and job-reset risks.
- Incomplete EventBridge/SNS alert wiring.
- Weak validation of model output.
- Risk scores that can look reassuring when AI analysis fails.
- Financial rules that can misinterpret legitimate invoices.
- Frontend polling that does not reliably refresh completed invoice details.
- A broken OCR test import.
- Deployment packaging and configuration reproducibility problems.

This is **Generative AI inference**, not RAG, autonomous Agentic AI, or an ML training/MLOps platform.

## 2. Project Overview

### Purpose and likely users

The application converts invoice documents into structured records and review signals.

Likely users are finance staff, accounts-payable reviewers, auditors, or small-business operators. These roles are inferred from the interface and workflow; the repository does not establish a real customer base.

### Implemented capabilities

- Email registration, confirmation, sign-in, and sign-out.
- Authenticated API requests.
- Direct upload of supported document MIME types to S3.
- Background OCR and AI analysis.
- Deterministic invoice checks.
- Risk scores from 0 to 100.
- LOW, MEDIUM, and HIGH risk classifications.
- Invoice listing and detail views.
- Invoice deletion.
- Processing-status endpoint and frontend polling.
- Risk, vendor, and anomaly analytics.
- Infrastructure definitions and deployment workflow files.

### Partial capabilities

- User isolation: invoice access is scoped, but job-status and browser-cache gaps remain.
- Processing-status experience: jobs exist, but the list primarily exposes completed invoice records.
- Date filtering: visible in the frontend, ignored by the backend.
- Automatic result display: status polling exists, but detail refresh is not connected to completion.
- Notifications: publisher, rule, and topic exist, but their wiring is incomplete.
- CI/CD: workflow definitions exist; operational configuration and successful runs are unverified.
- Schema validation: Pydantic models exist but are not used to validate the main pipeline.

### What it does not implement

- Invoice payment or accounting-ledger posting.
- ERP integration.
- Human approval, rejection, correction, or reassignment workflows.
- Retrieval over historical invoices for AI reasoning.
- Vendor-price databases or verified tax-reference lookups.
- Embeddings or a vector database.
- Autonomous tool selection.
- LangChain or LangGraph.
- Model training, fine-tuning, experiment tracking, or drift detection.
- Demonstrated fraud-detection accuracy.
- Verified production capacity, availability, or cost.

The output is best described as **invoice review assistance**, not a final determination that fraud occurred.

## 3. Technology Stack

### Frontend

**React 18 and TypeScript**

React implements the login, dashboard, invoice list, invoice details, and analytics pages. TypeScript describes API response shapes and UI data.

Its practical role is a browser application with reusable components. The repository does not independently establish the original selection process.

**Vite 5**

Vite runs the local frontend on port 5173 and builds static assets. The build script runs TypeScript checking before Vite compilation.

**React Router**

Defines browser routes and the authenticated layout. The protected-route component controls navigation, while actual backend authentication is enforced by API Gateway.

**AWS Amplify**

Configures Cognito and performs sign-up, confirmation, sign-in, session retrieval, token retrieval, and sign-out.

**Axios**

Sends authenticated API requests and uploads invoice bytes to a presigned S3 URL. These are separate paths: the S3 upload does not pass through the API client.

**TanStack React Query**

Caches backend data, retries queries, and polls invoice status. Its user-independent query keys create an account-switching concern.

**Zustand**

Maintains in-memory authentication display state, invoice filters, and active upload progress.

**Tailwind CSS, Recharts, date-fns, and clsx**

Provide styling, charts, date formatting, and conditional CSS classes.

### Backend

**Python 3.12**

The runtime configured for the eight application Lambdas.

**Boto3 and botocore**

Provide AWS service clients and AWS exception handling for S3, DynamoDB, Textract, Bedrock, Step Functions, and EventBridge.

**Pydantic**

Defines intended data models, including invoices, anomalies, jobs, and pipeline payloads. The handlers primarily pass dictionaries and do not instantiate these models.

Therefore, Pydantic is an available modeling dependency, **not an enforced validation boundary**.

### Infrastructure and delivery

**AWS CDK v2 with TypeScript**

Defines five CloudFormation stacks. Infrastructure package versions include `aws-cdk-lib` 2.266.0 and CDK CLI 2.1138.0.

**GitHub Actions**

Defines backend tests and deployment, frontend build and deployment, and pull-request checks.

**PowerShell and AWS CLI**

Support documented manual deployment, Lambda-layer repairs, and log inspection.

**Docker**

Appears as a CDK dependency-bundling fallback. There is no application Dockerfile or ECS/Kubernetes deployment.

### Testing

**pytest and pytest-cov**

Used by backend test workflows.

**Moto**

Listed as a test dependency, but the inspected tests do not implement a mocked end-to-end AWS pipeline.

## 6. Current Architecture

The current architecture is a **serverless web application with an asynchronous document-processing workflow**.

It has separate function responsibilities, but “eight Lambdas” alone does not establish eight independently owned microservices.

```text
Browser
  ├── CloudFront ── private S3 frontend
  ├── Cognito authentication
  │
  └── API Gateway + Cognito authorizer
        ├── Upload Lambda ── processing_jobs
        │       └── returns presigned S3 PUT URL
        ├── Invoices Lambda ── invoices / processing_jobs
        └── Analytics Lambda ── tenant invoice queries

Browser ── document bytes ── S3 uploads
                               │
                               ▼
                              SQS ── repeated trigger failures ── DLQ
                               │
                               ▼
                         Trigger Lambda
                               │ StartExecution
                               ▼
                      Step Functions Express
                      OCR → AI → Risk → Store
                       │     │            ├── DynamoDB invoices
                   Textract Bedrock       ├── DynamoDB jobs
                                          ├── S3 extracted text
                                          └── EventBridge publication
                                               [alert wiring incomplete]

Browser ── status/detail/analytics requests ── API Gateway
```

### Infrastructure ownership

- **StorageStack:** upload, processed, and an additional frontend bucket; two DynamoDB tables; SQS and DLQ; S3 notification.
- **AuthStack:** Cognito pool and browser client.
- **ProcessingStack:** five processing/trigger Lambdas, shared layer, workflow, alert topic/rule, and DLQ alarm.
- **ApiStack:** three API Lambdas, shared layer, REST API, authorization, and CORS.
- **FrontendStack:** a separate hosting bucket, CloudFront, optional static deployment, and an unused additional shared layer.

The StorageStack frontend bucket is not the bucket used by FrontendStack’s CloudFront distribution.

### Classification

**IMPLEMENTED:** frontend, authenticated API definitions, direct upload, queue bridge, four-stage workflow, OCR/model calls, deterministic scoring, persistence, analytics.

**PARTIAL:** tenant isolation, notifications, validation, UI refresh, lifecycle management, reproducible delivery.

**DOCUMENTED/INTENDED:** confirmed email alerts, reliable automatic deployment, broad production-readiness claims.

**FUTURE/PROPOSED:** agents, WebSockets, materialized analytics, multi-region extensions.

**UNVERIFIED:** current AWS resources, model access, delivery subscriptions, CI secrets, live traffic, actual operational metrics.

**NOT PRESENT:** RAG, embeddings, vector storage, autonomous agents, ML training.

## 7. Application / Request Flow

### Flow A — Registration and login

1. F1 configures Amplify before rendering.
2. F2 exposes login, registration, and confirmation modes.
3. Amplify calls Cognito.
4. The frontend fetches the current user and session.
5. Zustand records the user for UI rendering.
6. The API interceptor retrieves the ID token and adds an Authorization header.
7. API Gateway uses the Cognito authorizer.
8. B10 extracts the validated `sub` claim as `tenant_id`.

```text
Login form → Amplify → Cognito
                       ↓
                  ID token/session
                       ↓
API request → Cognito authorizer → claims.sub → tenant_id
```

The frontend route guard is a UI control. Backend protection comes from API Gateway and application ownership checks.

### Flow B — Upload and processing

1. The upload UI accepts one selected file.
2. F3 checks MIME type and a 10 MiB browser-side limit.
3. `POST /invoices/upload-url` reaches B1.
4. B1 derives the tenant from claims.
5. It generates an ID resembling `inv_YYYYMMDD_<random-suffix>`.
6. It creates `job_<invoice_id>` in PENDING state.
7. It returns a five-minute presigned PUT URL.
8. The browser uploads directly to the generated S3 key.
9. S3 sends an ObjectCreated event for the `invoices/` prefix to SQS.
10. B4 reads the first nested S3 record.
11. B4 extracts tenant and invoice ID from the object key.
12. It writes the job again and starts an Express execution.
13. B5 calls Textract `analyze_expense`.
14. The parser extracts the first expense document.
15. B6 sends structured fields and raw text to Nova Micro.
16. B7 computes risk and builds the combined anomaly list.
17. B8 saves extracted text, writes the completed invoice, marks the job complete, and attempts event publication.

### Flow C — Status and display

```text
Upload completes → navigate to invoice detail
                         ├── detail query
                         └── status query every 3 seconds
```

Before storage finishes, the detail query can return 404.

The status query eventually stops on COMPLETED or FAILED, but it does not invalidate the detail query. Therefore, a successful pipeline does not guarantee that the displayed error or empty detail view automatically recovers.

The failure banner also disappears for FAILED rather than presenting the job’s error message.

### Flow D — Analytics

Each analytics endpoint retrieves all invoices for the authenticated tenant through paginated DynamoDB **Query** calls.

It calculates:

- Total and completed invoice counts.
- Risk-level counts.
- Average score.
- Average recorded processing time.
- Daily score averages.
- Vendor averages.
- Anomaly-type counts.

There is no separate aggregate store.

### Flow E — Deletion

1. Read the invoice using tenant and invoice ID.
2. Attempt to delete the original S3 object.
3. Log S3 deletion failure without stopping.
4. Delete the DynamoDB invoice record.

The job record, processed text, and historical S3 versions are not comprehensively removed by this flow.

### Realistic scoring example

Assume OCR returns:

- Total: 100.
- Line-item prices: 50 and 30.
- All four required fields present.
- A normal invoice number.
- No duplicate descriptions.
- One HIGH-severity AI anomaly.

The deterministic math check adds 40. The AI anomaly adds 15.

**Result: 55, MEDIUM.**

This is an illustrative execution of the scoring formula, not a measured AWS run.

## 8. Project-Specific Technical Analysis

### OCR behavior

B5 calls synchronous Textract `AnalyzeExpense`.

The parser:

- Reads only `ExpenseDocuments[0]`.
- Extracts invoice number, vendor, dates, total, subtotal, tax, and line items.
- Retains values largely as strings.
- Collects LINE block text.
- Defaults currency to USD.
- Does not preserve field-level confidence or coordinates.
- Does not normalize dates or monetary values.

PDF/TIFF acceptance does not establish arbitrary multipage support. AWS documents synchronous single-page PDF support and separate asynchronous expense-analysis operations. [AWS Textract documentation](https://docs.aws.amazon.com/textract/latest/dg/analyzing-document-expense.html), [single-page PDF support](https://aws.amazon.com/about-aws/whats-new/2022/01/amazon-textract-pdf-processing-jpeg-encoded-images/).

### AI implementation

**Model:** `us.amazon.nova-micro-v1:0`  
**Provider:** Amazon Bedrock  
**Invocation:** `bedrock_runtime.invoke_model`  
**Input:** One user message containing structured fields and raw OCR text.  
**Output target:** JSON with anomalies, summary, and confidence.

Configuration:

- `maxTokens`: 1500.
- Temperature: 0.2.
- Top-p: 0.9.
- Up to five application-level attempts: the initial attempt plus four retries.

There is no separate system-message object. The role instruction is inside the user prompt.

### Parsing is not validation

`_parse_json_response()` attempts:

1. Direct JSON parsing.
2. Removal of markdown fences.
3. Extraction between the first opening and final closing brace.
4. A fallback object when parsing fails.

But valid JSON can still have the wrong shape.

Examples:

- A JSON list instead of an object.
- `anomalies: null`.
- Anomalies containing strings.
- Missing or unsupported severities.
- Confidence outside the intended range.

B11 defines helpful types, but B6 does not apply them.

### AI failure behavior

Handled Bedrock errors produce:

- Empty anomalies.
- An “analysis unavailable” summary.
- Confidence 0.

The pipeline then continues through deterministic scoring and stores COMPLETED.

This preserves extraction availability, but **completion and analysis quality are conflated**. A low score after AI failure should not be interpreted as equivalent to a fully analyzed low-risk invoice.

### RAG and agents

There is no database retrieval feeding historical context into the prompt.

There are no embeddings, chunk retrieval, vector search, model-selected tools, or iterative agent decisions.

Step Functions provides fixed orchestration. That does not make the model agentic.

### Exact risk formula

- Math discrepancy: **40**.
- Missing invoice number: **8**.
- Missing receipt date: **8**.
- Missing total: **8**.
- Missing vendor: **8**.
- Purely numeric invoice number shorter than three digits: **10**.
- Repeated normalized item description: **15**.
- Each AI HIGH anomaly: **15**.
- Each AI MEDIUM anomaly: **7**.
- Each AI LOW or unrecognized severity: **3**.
- Maximum score: **100**.

Bands:

- **LOW:** 0–29.
- **MEDIUM:** 30–69.
- **HIGH:** 70–100.

### Financial limitations

The math rule compares the sum of extracted `price` values directly with total.

It does not explicitly reconcile:

- Tax.
- Discounts.
- Shipping.
- Credits.
- Unit price versus line total.
- Quantity.
- Negative amounts.
- Locale-specific decimal separators.

Removing all characters except digits and periods can turn negative amounts positive and misinterpret some number formats.

Amounts expressed entirely in words become zero in the parser used by this rule, which can skip the discrepancy check.

The duplicate rule treats repeated descriptions as duplicates even when quantities, prices, or legitimate repeated purchases differ.

AI and deterministic findings can describe the same issue and both contribute to the score.

### Rate limiter

The limiter is local to one warm Lambda environment.

It does not coordinate across concurrent instances. It also records the pre-sleep timestamp after sleeping, weakening the intended rolling-window behavior.

Waiting inside a Lambda with a 60-second timeout can itself cause timeout risk.

### Processing time

The stored timing sums OCR time, AI time, and a partial storage interval.

It excludes queue delay, trigger time, orchestration overhead, risk-stage timing, and operations occurring after the timing calculation.

It is **not end-to-end user latency**.

## 9. Data / State / Memory

### Durable storage

**Upload S3 bucket**

Stores originals under a tenant-prefixed generated key. Versioning is enabled.

**Processed S3 bucket**

Stores extracted text under:

```text
processed-text/{tenant_id}/{invoice_id}.txt
```

The current storage handler does not write complete OCR and analysis JSON artifacts to this bucket.

**Invoices table**

- Partition key: `tenant_id`.
- Sort key: `invoice_id`.
- Contains completed invoice data, findings, score, explanation, and object references.

**Processing-jobs table**

- Partition key: `job_id`.
- Contains tenant, invoice ID, status, stage, and timestamps.

The table enables TTL on `ttl`, but `create_job()` does not populate that field. Automatic expiry is therefore incomplete.

### Workflow state

The workflow carries a growing JSON payload containing identifiers, OCR data, AI output, and risk findings.

There is no artifact-pointer strategy for large intermediate results. Larger documents therefore increase workflow-payload and final-record size risk.

### Temporary state

- Zustand authentication display state.
- Upload-progress entries.
- Invoice filters.
- React Query caches.
- Per-Lambda rate-limiter timestamps.

These are not durable business records.

### Restart behavior

A page reload recreates UI state and query caches, then attempts Cognito session restoration.

Completed records remain in AWS storage, assuming the resources still exist.

Active upload progress is lost on reload. There is no durable frontend recovery mechanism for the upload list.

A cold Lambda environment resets the local limiter.

### No conversational memory

The AI call is independent per invoice. There is no chat history, conversation state, or long-term model memory.

## 12. Security

### Implemented controls

- Cognito authorizer attached to application API methods.
- User ID taken from validated authorizer claims.
- Tenant-prefixed generated upload keys.
- Short-lived presigned URLs.
- Explicit content-type allowlist.
- Private S3 buckets.
- Upload and processed bucket encryption configuration.
- CloudFront OAC and HTTPS redirect.
- Cognito password complexity and email confirmation.
- Per-function IAM roles and resource grants.
- API request-body tracing disabled.
- GitHub OIDC workflow configuration instead of embedded AWS access keys.

### High-priority gaps

**Job-status ownership**

B2 first performs a tenant-scoped invoice lookup, then retrieves `job_<invoice_id>` without comparing its `tenant_id` with the requester.

Someone who knows another invoice ID may receive its job status, stage, or error details.

**Browser cache isolation**

F4 uses query keys without user identity. F5 signs out and clears auth state but not the query cache or upload/filter state.

A second user in the same SPA session can receive cached data from the preceding session before or instead of a fresh request.

**Upload enforcement**

The size limit is browser-side. The backend does not verify uploaded content, actual object size, page count, or document structure before OCR.

**Published demo credentials**

Deployment notes contain explicit demo passwords. Their current validity is unverified. They should not be reused for a live account, and any still-valid published password should be rotated.

### Other gaps

- Bedrock invocation and EventBridge publication use wildcard resources.
- No application-specific rate limits, tenant budgets, or processing concurrency controls.
- No MFA configuration.
- No role hierarchy or organization membership model.
- No completed password-reset UI.
- Broad S3 CORS.
- API Gateway-generated errors always use the first allowed origin, which is localhost.
- One unsupported-content-type response omits the request event needed for dynamic CORS.
- No explicit security-header policy for the frontend.
- No complete sensitive-data retention/deletion policy.
- Step Functions error logs include execution data, which may contain invoice content.
- A malformed AI response is logged partially.

### Prompt injection

Invoice text is untrusted and is concatenated into the same prompt as the task instructions.

No explicit prompt-injection defense, guardrail configuration, or post-generation schema enforcement is implemented.

The model cannot invoke tools here, but malicious document instructions could still alter findings or summaries.

## 13. Error Handling & Troubleshooting

### Existing behavior

**Upload/API failures**

Handlers return JSON error responses for many failures. The analytics `ValueError` path is inconsistent: it returns a raw body without the shared response headers.

**OCR failures**

Textract client errors update the job and raise an OCR exception. Workflow catches attempt to mark the job failed.

**AI failures**

Selected Bedrock errors are converted into a nonfatal result. Network errors, timeouts, and wrong-shaped JSON are not all covered by that fallback.

**Storage failures**

S3 text-save and EventBridge client errors are treated as nonfatal. DynamoDB invoice/job write failures propagate.

**Queue-trigger failures**

The trigger raises an exception. The event-source configuration enables partial batch failures, but the handler does not return the required partial-failure structure. Batch size is currently one.

### Critical boundary: DLQ coverage

The trigger starts the workflow asynchronously and returns.

A later OCR or storage failure does not automatically return the original SQS message to the queue.

Therefore, the SQS DLQ primarily protects the **trigger/start handoff**, not every processing-stage failure.

### Failure-state mismatch

I4’s failure handler sets job status and a timestamp, but does not preserve the detailed stage/error fields present in I7.

It also ends on a successful DynamoDB update instead of transitioning to an explicit Fail state. A workflow can therefore finish successfully at the orchestration level while the application job is marked FAILED.

### Practical investigation order

```text
Browser request and invoice ID
  → upload API
  → S3 object
  → SQS/trigger logs
  → job record
  → workflow logs
  → OCR/AI/risk/store logs
  → invoice record
  → frontend query/cache behavior
```

`watch-pipeline.ps1` reads recent logs. It is a diagnostic utility, not an automated correctness test.

**EVIDENCE:** B2 `_get_status()`, B9 `get_job()`.

**SEVERITY:** HIGH.

**EVIDENCE:** F4/F5.

## 22. Architecture / Design Decisions

The following reasoning is defensible engineering analysis. Where documentation gives a rationale, it is still not independent proof of the original decision process.

### Direct S3 upload

**REQUIREMENT:** Accept invoice files.  
**CURRENT CHOICE:** Presigned PUT URL.  
**WHY:** Avoids transporting file bytes through application handlers.  
**TRADE-OFF:** Upload completion and document validation become separate concerns.  
**ALTERNATIVE:** Backend-mediated upload or constrained presigned POST.  
**WHEN UNSUITABLE:** When mandatory inspection must occur before any object enters the normal ingestion path.

### SQS before workflow launch

**REQUIREMENT:** Buffer upload events and retry failed handoffs.  
**CURRENT CHOICE:** Standard SQS plus trigger Lambda.  
**WHY:** Provides a queue boundary and DLQ for launch failures.  
**TRADE-OFF:** Duplicate delivery remains possible; downstream concurrency needs separate control.  
**ALTERNATIVE:** Direct event routing for simpler workloads.  
**WHEN UNSUITABLE:** When ordering or more specialized scheduling is required.

### Step Functions Express

**REQUIREMENT:** Coordinate short processing stages.  
**CURRENT CHOICE:** Asynchronous Express workflow.  
**WHY:** Explicit stage sequence, retries, and catches.  
**TRADE-OFF:** Requires idempotent design and log-based execution investigation.  
**ALTERNATIVE:** Standard workflow or a simpler single function.  
**WHEN UNSUITABLE:** Long waits, human approvals, or longer OCR jobs.

### DynamoDB

**REQUIREMENT:** Store variable invoice records and job state.  
**CURRENT CHOICE:** Composite-key invoice table and separate jobs table.  
**WHY:** Fits key-based reads and document-like records.  
**TRADE-OFF:** Aggregation and alternate sorting require deliberate access-pattern design.  
**ALTERNATIVE:** Relational storage for accounting relationships and reporting.  
**WHEN UNSUITABLE:** Complex joins and transactional accounting become central.

### Textract AnalyzeExpense

**REQUIREMENT:** Extract invoice-specific fields.  
**CURRENT CHOICE:** Expense extraction rather than generic text OCR.  
**WHY:** Produces useful summary and line-item structures.  
**TRADE-OFF:** Extraction still needs normalization and quality checks.  
**ALTERNATIVE:** Generic OCR plus custom parsing, or asynchronous expense analysis.  
**WHEN UNSUITABLE:** Document types or lengths exceed the chosen path.

### Bedrock Nova Micro

**REQUIREMENT:** Generate semantic findings from invoice text.  
**CURRENT CHOICE:** One text-model invocation through AWS IAM.  
**WHY:** Integrates with the existing AWS application.  
**TRADE-OFF:** Model output is probabilistic and lacks external business references.  
**ALTERNATIVE:** Another evaluated model or rules-only processing.  
**WHEN UNSUITABLE:** Evaluation shows inadequate accuracy or missing capabilities.

### Polling

**REQUIREMENT:** Display asynchronous progress.  
**CURRENT CHOICE:** Three-second status polling.  
**WHY:** Simple frontend integration.  
**TRADE-OFF:** Repeated requests and delayed update visibility.  
**ALTERNATIVE:** Push notifications.  
**WHEN UNSUITABLE:** Measured polling cost or concurrent-client load warrants replacement.

### Interviewer Pressure Questions

Use these concise answers alongside the detailed bank.

**“You said this is Agentic AI. Where does the model choose a tool?”**  
“It does not. The accurate description is a fixed workflow with Generative AI analysis.”

**“You said RAG. Show me the retrieval code.”**  
“There is no retrieval implementation. The model receives the current invoice’s extracted content.”

**“You said users can never see each other’s data. What about the jobs table?”**  
“The current job-status fallback lacks an ownership comparison. Complete isolation is not a defensible claim yet.”

**“You said retries are safe. Why does each execution get a random name?”**  
“That is a gap. The current code does not implement complete idempotency.”

**“You said the DLQ catches OCR failures. When is the SQS message acknowledged?”**  
“The trigger returns after starting the workflow. Later OCR failures are outside that queue retry boundary.”

**“You said the rules are 100% reliable. What about tax?”**  
“The arithmetic is deterministic, but the financial assumptions are incomplete. Tax and other adjustments need explicit handling.”

**“You said the score is low. What if Bedrock was unavailable?”**  
“AI failure can reduce the score. A separate analysis-quality state is needed.”

**“You said an email was sent. Where is the subscription?”**  
“No subscription is defined in the repository, and the event bus wiring also needs correction.”

**“You said this takes three seconds end to end. What exactly is timed?”**  
“The stored value is a partial sum of stage times. It is not a valid end-to-end benchmark.”

**“You said CI/CD is operational. Can you prove a successful run?”**  
“Not from the local repository. Workflow definitions exist, but runtime success and secrets are unverified.”

**“What did you personally implement?”**  
“I would answer using my actual contributions and evidence. I would not claim ownership of every repository component solely because I can explain it.”
